  This is the answer to 'how do I show the new fields taking effect on the node?'
  /configz is the kubelet's own debug endpoint, reached through the API server
  proxy. It returns the EFFECTIVE running config -- not what we asked for, but
  what the kubelet is actually operating with.

      FIELD                        ASKED FOR          KUBELET RUNNING    MATCH NOTE

      evictionHard                 {"memory.availabl  {"memory.availabl  yes   +2 defaults

▸ THE PAYOFF -- same expression, different resolved values

$ kubectl get nodes -l 'karpenter.sh/nodepool in (demo-2-small,demo-2-large)'       -o custom-columns='NODEPOOL:.metadata.labels.karpenter\.sh/nodepool,INSTANCE:.metadata.labels.node\.kubernetes\.io/instance-type,VCPU:.status.capacity.cpu,MAXPODS:.status.allocatable.pods,ALLOC-CPU:.status.allocatable.cpu,ALLOC-MEM:.status.allocatable.memory'
NODEPOOL       INSTANCE    VCPU   MAXPODS   ALLOC-CPU   ALLOC-MEM
demo-2-small   m5.large    2      16        1940m       7724592Ki
demo-2-large   m5.xlarge   4      32        3880m       15887436Ki

  Expected
    maxPods = "vcpus * 8"
      m5.large   2 vCPU  ->  16 pods
      m5.xlarge  4 vCPU  ->  32 pods

    kubeReserved.cpu = "max(60, vcpus * 30)"
      m5.large           ->  60m    (max(60, 60))
      m5.xlarge          ->  120m   (max(60, 120))

    systemReserved.cpu = "max(20, vcpus * 10)"
      m5.large           ->  20m    (max(20, 20))
      m5.xlarge          ->  40m    (max(20, 40))

  ALLOC-CPU is capacity minus BOTH reservations, so the column above should read
  1920m on m5.large (2000 - 60 - 20) and 3840m on m5.xlarge (4000 - 120 - 40).

▸ Proof the resolved reservations reached the kubelet -- and the math closes
  demo-2-small
      kubeReserved.memory   = 96Mi    <- resolved from "memory_mib / 100"
      systemReserved.memory = 0       <- resolved from "memory_mib / 200"
      capacity                                     7739.5
      - kubeReserved.memory                         -96.0
      - systemReserved.memory                         0.0
      - evictionHard[memory.available] (100Mi)     -100.0
      = computed allocatable                       7543.5
        reported allocatable                       7543.5
        closes?                                       yes

  demo-2-large
      kubeReserved.memory   = 176Mi   <- resolved from "memory_mib / 100"
      systemReserved.memory = 0       <- resolved from "memory_mib / 200"
      capacity                                    15791.1
      - kubeReserved.memory                        -176.0
      - systemReserved.memory                         0.0
      - evictionHard[memory.available] (100Mi)     -100.0
      = computed allocatable                      15515.1
        reported allocatable                      15515.1
        closes?                                       yes

  Why this matters
    kubeReserved.memory here is not a number anyone typed -- it is
    "memory_mib / 100" evaluated against each instance type, rounded up to a 16Mi
    boundary, and handed to the kubelet. The arithmetic closing proves the resolved
    value is what the kubelet is really reserving.

  BEAT 3 of 4 -- Invalid configuration never reaches a node
════════════════════════════════════════════════════════════════

  These four NodeClasses have no NodePools. Nothing launches. That is the point.

▸ 3d. Semantically invalid                 4 distinct rule violations
  demo-3d-semantics
    ValidationSucceeded : False
    reason              : InvalidKubeletConfiguration
    message             : spec.kubelet.evictionHard[nodefs.available]: "150%" must be a
                          percentage or a resource quantity; spec.kubelet.evictionHard:
                          "notarealsignal" isn't a valid eviction signal, must be one of
                          memory.available, nodefs.available, nodefs.inodesFree,

  Why each one matters
    3a  a compile check alone catches this
    3b  a compile check does not -- only per-instance-type evaluation finds it
    3c  the API server cannot catch this: spec.kubelet is an open map, so the
        typo is caught by strict-decoding against k8s.io/kubelet
    3d  all four violations decode cleanly against the Go types; they are only
        wrong semantically, which is what validateKubeletSemantics is for

  BEAT 4 of 4 -- Silent-drop prevention across AMI families
════════════════════════════════════════════════════════════════
  Only AL2023 renders the raw kubelet config through to the node.
  Other families apply only the subset Karpenter explicitly maps.
  Without this check, extra fields are accepted, stored, then quietly discarded.

▸ Apply three NodeClasses on non-AL2023 families

$ kubectl apply -f 04-unsupported.yaml
ec2nodeclass.karpenter.k8s.aws/demo-4a-bottlerocket unchanged
ec2nodeclass.karpenter.k8s.aws/demo-4b-al2 unchanged
ec2nodeclass.karpenter.k8s.aws/demo-4c-al2-supported unchanged

▸ 4a. Bottlerocket -- unmanaged fields AND podsPerCore
  demo-4a-bottlerocket
    ValidationSucceeded : False
    reason              : UnsupportedKubeletConfiguration
    message             : spec.kubelet has fields not applied by the Bottlerocket AMI family
                          that would be silently dropped: podsPerCore, registryBurst,
                          serializeImagePulls
  podsPerCore IS mapped by Karpenter, but Bottlerocket has no setting to
  render it into (PodsPerCoreEnabled = false), so it is rejected too.

▸ 4b. AL2 -- same unmanaged fields, but podsPerCore is supported here
  demo-4b-al2
    ValidationSucceeded : False
    reason              : UnsupportedKubeletConfiguration
    message             : spec.kubelet has fields not applied by the AL2 AMI family that
                          would be silently dropped: containerLogMaxSize, podPidsLimit
  Note podsPerCore is ABSENT from this message. The check is per-family,
  not a blanket denial.

▸ 4c. Positive control -- AL2 restricted to fields it can actually apply
  demo-4c-al2-supported
    ValidationSucceeded : True
    reason              : ValidationSucceeded

  Accepted -- including a CEL expression on kubeReserved, a managed field.
  Extended config is not 'AL2023-only'. It is 'whatever your family can apply'.

  The point
    The alternative to this check is a node that comes up without the
    configuration you asked for, with nothing anywhere telling you -- only
    discoverable by SSH-ing to the node and reading the kubelet config.
