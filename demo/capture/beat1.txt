  BEAT 1 of 4 -- Extended kubelet configuration
════════════════════════════════════════════════════════════════
  spec.kubelet used to be a closed struct with ~11 hardcoded fields.
  It is now an open map validated against the upstream k8s.io/kubelet type.

▸ The configuration we are about to apply

$ grep -A 30 '  kubelet:' 01-extended.yaml | grep -v '^\s*#'

    evictionHard:
      memory.available: 10%

      memory.available: 15%

      memory.available: 1m30s

▸ THE PROOF -- ask the running kubelet what config it is using
  This is the answer to 'how do I show the new fields taking effect on the node?'
  /configz is the kubelet's own debug endpoint, reached through the API server
  proxy. It returns the EFFECTIVE running config -- not what we asked for, but
  what the kubelet is actually operating with.

$ kubectl get --raw "/api/v1/nodes/ip-192-168-27-86.us-west-2.compute.internal/proxy/configz"
    NEW -- only expressible with the extended config:
      FIELD                        ASKED FOR          KUBELET RUNNING    MATCH NOTE
      --------------------------------------------------------------------------------------
      containerLogMaxFiles         6                  6                  yes   
      containerLogMaxSize          "20Mi"             "20Mi"             yes   
      maxParallelImagePulls        5                  5                  yes   
      podPidsLimit                 4096               4096               yes   
      registryBurst                20                 20                 yes   
      registryPullQPS              10                 10                 yes   
      topologyManagerPolicy        "best-effort"      "best-effort"      yes   

    PRE-EXISTING -- the closed struct had these, and they still work:
      FIELD                        ASKED FOR          KUBELET RUNNING    MATCH NOTE
      --------------------------------------------------------------------------------------
      cpuCFSQuota                  false              false              yes   
      evictionHard                 {"memory.availabl  {"memory.availabl  yes   +2 defaults
      evictionMaxPodGracePeriod    60                 60                 yes   
      evictionSoft                 {"memory.availabl  {"memory.availabl  yes   
      evictionSoftGracePeriod      {"memory.availabl  {"memory.availabl  yes   
      imageGCHighThresholdPercent  85                 85                 yes   
      imageGCLowThresholdPercent   80                 80                 yes   

    14 of 14 fields applied as asked.
    ("+N defaults" means the kubelet merged the AMI family's defaults in
     alongside the key we set -- the value we asked for is unchanged.)
  This is the proof. ASKED FOR is spec.kubelet as stored on the EC2NodeClass.
  KUBELET RUNNING comes from the kubelet's own /configz endpoint. One node, so a
  match means the kubelet applied exactly what was asked -- there is no second node
  whose differences have to be explained away.

  Both tables matter, for different reasons:
    NEW           fields the closed struct could not express at all.
    PRE-EXISTING  proof the open map did not regress what already worked.

▸ Secondary: the UserData Karpenter rendered
  Weaker evidence than /configz -- it proves KARPENTER emitted the fields, not
  that the kubelet accepted them. Useful for showing the passthrough mechanism.
  No launch template found -- it is created on first node launch.
