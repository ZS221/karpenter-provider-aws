  BEAT 1 of 4 -- Extended kubelet configuration
════════════════════════════════════════════════════════════════
  spec.kubelet used to be a closed struct with ~11 hardcoded fields.
  It is now an open map validated against the upstream k8s.io/kubelet type.

▸ The configuration we are about to apply

$ grep -A 30 '  kubelet:' 01-extended.yaml | grep -v '^\s*#'

▸ THE PROOF -- ask the running kubelet what config it is using
  This is the answer to 'how do I show the new fields taking effect on the node?'
  /configz is the kubelet's own debug endpoint, reached through the API server
  proxy. It returns the EFFECTIVE running config -- not what we asked for, but
  what the kubelet is actually operating with.

$ kubectl get --raw "/api/v1/nodes/ip-192-168-27-86.us-west-2.compute.internal/proxy/configz"
    Only expressible with the extended config:
      FIELD                        CONTROL (baseline)     demo-1-extended       
      --------------------------------------------------------------------------
      registryBurst                10                     20                      <-- CHANGED
      registryPullQPS              5                      10                      <-- CHANGED
      maxParallelImagePulls        "<absent>"             5                       <-- CHANGED
      podPidsLimit                 -1                     4096                    <-- CHANGED
      containerLogMaxSize          "10Mi"                 "20Mi"                  <-- CHANGED
      containerLogMaxFiles         5                      6                       <-- CHANGED
      topologyManagerPolicy        "none"                 "best-effort"           <-- CHANGED

    Supported before this change too:
      FIELD                        CONTROL (baseline)     demo-1-extended       
      --------------------------------------------------------------------------
      evictionHard                 {"memory.available":   {"memory.available":    <-- CHANGED
      evictionSoftGracePeriod      "<absent>"             {"memory.available":    <-- CHANGED
      evictionMaxPodGracePeriod    "<absent>"             60                      <-- CHANGED
      imageGCHighThresholdPercent  85                     85                    
      imageGCLowThresholdPercent   80                     80                    
      cpuCFSQuota                  true                   false                   <-- CHANGED
      maxPods                      16                     29                      <-- CHANGED

  This is the proof. These are the values the kubelet is RUNNING with, read from
  its own /configz endpoint -- not what we asked for, and not merely what Karpenter
  rendered.

  maxPods differs for an unrelated reason: demo-1-extended sets no maxPods, so it
  falls back to the ENI-derived limit (29 on m5.large), while the control node has
  the beat-2 CEL expression resolving to 16. Not an extended-config effect.

▸ Secondary: the UserData Karpenter rendered
  Weaker evidence than /configz -- it proves KARPENTER emitted the fields, not
  that the kubelet accepted them. Useful for showing the passthrough mechanism.
  No launch template found -- it is created on first node launch.

  BEAT 2 of 4 -- CEL expressions resolved per instance type
════════════════════════════════════════════════════════════════
  The headline: one manifest, one expression, different config per node.

▸ The configuration -- note these are STRINGS, not numbers

$ grep -A 6 '  kubelet:' 02-cel-scaling.yaml
  kubelet:
    maxPods: "vcpus * 8"
    kubeReserved:
      cpu: "max(60, vcpus * 30)"
      memory: "memory_mib / 100"
---
apiVersion: karpenter.sh/v1
  Variables: vcpus, memory_mib, default_enis, ips_per_eni, max_pods, instance_type
  Functions: min(), max()

▸ Apply the NodeClass + two NodePools pinned to different instance sizes

▸ THE PAYOFF -- same expression, different resolved values

$ kubectl get nodes -l 'karpenter.sh/nodepool in (demo-2-small,demo-2-large)'       -o custom-columns='NODEPOOL:.metadata.labels.karpenter\.sh/nodepool,INSTANCE:.metadata.labels.node\.kubernetes\.io/instance-type,VCPU:.status.capacity.cpu,MAXPODS:.status.allocatable.pods,ALLOC-CPU:.status.allocatable.cpu,ALLOC-MEM:.status.allocatable.memory'
NODEPOOL       INSTANCE    VCPU   MAXPODS   ALLOC-CPU   ALLOC-MEM
demo-2-small   m5.large    2      16        1940m       7724592Ki
demo-2-large   m5.xlarge   4      32        3880m       15887436Ki

  Expected
    maxPods = "vcpus * 8"
      m5.large   2 vCPU  ->  16 pods
      m5.xlarge  4 vCPU  ->  32 pods

    kubeReserved.cpu = "max(60, vcpus * 30)"
      m5.large           ->  60m reserved   (max(60, 60))
      m5.xlarge          ->  120m reserved  (max(60, 120))

  Reserved CPU shows up as capacity minus allocatable.
